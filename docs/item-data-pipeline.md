# Path of Building — Item Data Pipeline

A complete reference for how PoB acquires, stores, and uses item and modifier data,
from the raw game files through to a fully evaluated item in a build.

---

## 1. Data Acquisition — From GGPK to Lua

All game data originates in `Content.ggpk`, GGG's monolithic binary bundle shipped
with the game client. There is no public API.

### 1.1 Extraction

`src/Export/ggpk/bun_extract_file.exe` reads the GGPK and extracts three categories
of files into a local working directory:

| Category | Format | Purpose |
|---|---|---|
| `Data/*.datc64` | Binary, GGG proprietary | All game tables (items, mods, skills, etc.) |
| `Metadata/StatDescriptions/*.txt` | UTF-16LE text | Human-readable stat description templates |
| `Metadata/Items/**/*.it` | Text | Item class tag inheritance hierarchy |
| `Metadata/Monsters/**/*.ot` | Text | Monster object files (for spectres/minions) |

### 1.2 The `.datc64` Binary Format

Each `.datc64` file is a flat binary table. The layout is:

```
[4 bytes]  row count (uint32 LE)
[N × row_size bytes]  fixed-width row data
[8-byte sentinel: 0xBB BB BB BB BB BB BB BB]
[variable data section]  strings and lists, referenced by byte offsets
```

Column types (defined in `src/Export/Classes/Dat64File.lua`):

| Type | Fixed size | Notes |
|---|---|---|
| `Bool` | 1 byte | 0 or 1 |
| `Int` / `UInt` / `Float` / `Enum` | 4 bytes | |
| `UInt16` | 2 bytes | |
| `Interval` | 8 bytes | two consecutive int32s |
| `String` | 8 bytes | uint64 offset into variable section → UTF-16LE string |
| `ShortKey` | 8 bytes | uint64 foreign row index into another table |
| `Key` | 16 bytes | uint64 row index + 8 bytes padding |
| `List` | 16 bytes | uint64 count + uint64 offset into variable section |

`0xFEFEFEFE` / `0xFEFEFEFEFEFEFEFE` is the null sentinel for foreign key columns.

### 1.3 Column Schema — `spec.lua`

`src/Export/spec.lua` is a manually maintained mapping of column names and types for
every `.dat` table. It is what allows the export scripts to access fields by name
(e.g. `mod.SpawnTags`) rather than raw byte offsets. This file must be updated
by hand whenever GGG adds or reorders columns in a patch.

### 1.4 Export Scripts

The scripts in `src/Export/Scripts/` run against the loaded `.datc64` tables through
a `dat("TableName"):Rows()` iterator API, and write out plain Lua data files into
`src/Data/`. Key scripts:

| Script | Output files |
|---|---|
| `bases.lua` | `src/Data/Bases/*.lua` |
| `mods.lua` | `src/Data/Mod*.lua` |
| `skills.lua` | `src/Data/Skills/*.lua` |
| `enchant.lua` | `src/Data/Enchantment*.lua` |
| `statdesc.lua` | `src/Data/StatDescriptions/*.lua` |
| `skillGemList.lua` | `src/Data/Gems.lua` |

The export tool itself is a mini GUI application (`src/Export/Launch.lua` +
`src/Export/Main.lua`) that runs inside PoB's own engine. All generated files carry
the header:

```lua
-- This file is automatically generated, do not edit!
-- Item data (c) Grinding Gear Games
```

## 2. Data Storage — The Lua Tables

After export, all game data lives as plain Lua tables loaded at startup.

### 2.1 Base Item Types

**Files:** `src/Data/Bases/*.lua` (one file per item class)

Each base type is a single table entry keyed by the display name:

```lua
itemBases["Jade Amulet"] = {
    type    = "Amulet",           -- item class
    tags    = { amulet = true, default = true },  -- spawn tag set
    influenceTags = {             -- influence-specific tag names
        shaper = "amulet_shaper",
        elder  = "amulet_elder",
        -- … all 8 influences
    },
    implicit = "+(20-30) to Dexterity",  -- implicit mod text (range encoded inline)
    implicitModTypes = { { "attribute" } },
    req  = { level = 5 },         -- level / str / dex / int requirements
    -- weapon-only fields:
    weapon = { PhysicalMin=…, PhysicalMax=…, CritChanceBase=…, AttackRateBase=…, Range=… },
    -- armour-only fields:
    armour = { ArmourBaseMin=…, ArmourBaseMax=…, EvasionBaseMin=…, … },
}
```

The `tags` table is the central link between a base type and its eligible modifier
pool. Tags are derived from two sources:

- The `.it` class inheritance chain (`Metadata/Items/…/*.it`) — each class file
  declares `tag = "..."` and may `extends` a parent class whose tags it inherits.
- The `Tags` column on the `BaseItemTypes` dat row.

Common tag examples: `amulet`, `ring`, `belt`, `str_armour`, `dex_armour`,
`int_armour`, `str_dex_armour`, `str_int_armour`, `dex_int_armour`,
`str_dex_int_armour`, `weapon`, `one_hand_weapon`, `two_hand_weapon`, `sword`,
`axe`, `mace`, `bow`, `staff`, `wand`, `claw`, `dagger`, `rapier`,
`helmet`, `body_armour`, `gloves`, `boots`, `shield`, `flask`, `jewel`, `default`.

### 2.2 Explicit Modifier Pool

**Files:** `src/Data/ModItem.lua`, `src/Data/ModFlask.lua`, `src/Data/ModJewel.lua`,
`src/Data/ModJewelAbyss.lua`, `src/Data/ModJewelCluster.lua`,
`src/Data/ModMaster.lua`, `src/Data/ModVeiled.lua`, `src/Data/ModMap.lua`,
`src/Data/ModNecropolis.lua`, `src/Data/ModGraft.lua`, `src/Data/ModTincture.lua`,
`src/Data/ModFoulborn.lua`

Each entry in the mod pool is keyed by a unique ID (GGG's internal mod ID, often
suffixed with the tier number):

```lua
["Strength8"] = {
    type      = "Suffix",           -- "Prefix", "Suffix", "Corrupted",
                                    -- "Synthesis", "1Shaper", "2Shaper", …
                                    -- "ScourgeUpside", "ScourgeDownside",
                                    -- "Exarch", "Eater", "DelveImplicit"
    affix     = "of the Titan",     -- display name / tier name
    "+(43-50) to Strength",         -- [1]: stat line(s) with inline roll range
    statOrder = { 1182 },           -- ordering hint for display
    level     = 74,                 -- minimum item level for this tier
    group     = "Strength",         -- mod family — only one tier per group per item
    weightKey = { "ring", "amulet", "belt", … "default" },
    weightVal = { 1000,   1000,    1000,  … 0        },
    modTags   = { "attribute" },    -- semantic tags (used for catalyst scaling)
    -- optional fields:
    weightMultiplierKey = { … },    -- secondary weight multiplier keys
    weightMultiplierVal = { … },    -- corresponding multipliers (applied as × val/100)
    tags = { "has_attack_mod" },    -- tags added to the item when this mod is present
}
```

A mod entry can have multiple stat lines; they appear as positional string values
`[1]`, `[2]`, etc., with `statOrder` giving a parallel index.

### 2.3 Enchantments

**Files:** `src/Data/EnchantmentHelmet.lua`, `EnchantmentBoots.lua`,
`EnchantmentGloves.lua`, `EnchantmentBody.lua`, `EnchantmentBelt.lua`,
`EnchantmentWeapon.lua`, `EnchantmentFlask.lua`

Enchantments are stored per slot and indexed by skill name, then by lab tier:

```lua
["Arc"] = {
    ["MERCILESS"] = {
        "25% increased Arc Damage",
        "Arc has +20% chance to Shock",
        "Arc deals 8% increased Damage for each time it has Chained",
    },
    ["ENDGAME"] = {
        "40% increased Arc Damage",
        "Arc Chains an additional time",
        -- …
    },
}
```

Enchantments are slot-specific by virtue of being in separate files. There are no
`weightKey`/`weightVal` fields — an enchant can go on any item of the matching slot
class, and only one enchant can exist per item.

### 2.4 Unique Items

**Files:** `src/Data/Uniques/*.lua`

Unique items are stored as raw text blocks, identical to what you would paste into
PoB from the in-game tooltip. They are matched by name at parse time and the text
is processed by the same `ParseRaw` pipeline as any other item.

Special uniques with variable mods (Watcher's Eye, Timeless Jewels, etc.) live in
`src/Data/Uniques/Special/` and use `Variant` directives to encode multiple
possible mod pools.

### 2.5 Skills and Gems

**Files:** `src/Data/Skills/*.lua`, `src/Data/Gems.lua`

Active and support skill definitions, per-level stat tables, and gem quality
bonuses. These are not directly involved in item mod eligibility.

## 3. Mod Eligibility — How Mods Are Assigned to Items

Eligibility is resolved entirely at runtime through two complementary lookups.
There is **no pre-built list** of "mods for this base"; it is computed on demand.

### 3.1 The Tag Matching Algorithm

Given a base type and a candidate mod entry, the spawn weight is determined by
`Item:GetModSpawnWeight()` in `src/Classes/Item.lua`:

```
weight = 0
for i, key in ipairs(mod.weightKey) do
    if item.base.tags[key]                 -- base has this tag
       or item has influence matching key  -- e.g. "amulet_shaper" for Shaper influence
    then
        weight = mod.weightVal[i]          -- use the paired weight value
        break                              -- first match wins; order matters
    end
end

-- Apply weight multiplier if present
for i, key in ipairs(mod.weightMultiplierKey or {}) do
    if item.base.tags[key] or influence match then
        weight = weight * mod.weightMultiplierVal[i] / 100
        break
    end
end
```

Key rules:
- **First match wins.** `weightKey` is an ordered list; the first tag that matches
  the item's tag set determines the weight.
- **Weight = 0 means ineligible.** The `"default"` key is always last in the list
  with `weightVal = 0` as a guard, preventing the mod from accidentally falling
  through to item types not explicitly listed.
- A mod not present in `weightKey` at all has an implicit weight of 0.

### 3.2 Item Level Gating (Tiers)

Within a `group`, multiple entries represent the tiers of that mod family. Each
entry has a `level` field — the minimum item level required for that tier to be
available:

```
tier eligible = (weight > 0) AND (item.itemLevel >= mod.level)
```

All eligible tiers within a group could theoretically roll; the actual tier chosen
in-game is weighted by the per-tier spawn weights. In PoB's crafting UI, all
eligible tiers are shown; you pick one explicitly.

### 3.3 Group Mutual Exclusion

Mods sharing the same `group` value are mutually exclusive — only one tier from
a group can be present on an item at a time. For example, `"Strength"` is a group;
an item can have `Strength7` or `Strength8`, never both.

### 3.4 Influence Mods

Influence mods use special `type` values rather than `"Prefix"` / `"Suffix"`:

| `type` value | Meaning |
|---|---|
| `"1Shaper"`, `"2Shaper"` | Shaper influence, tier 1 or 2 |
| `"1Elder"`, `"2Elder"` | Elder influence |
| `"1Adjudicator"` … | Conqueror influences (Warlord, Hunter, Redeemer, Crusader) |
| `"Synthesis"` | Synthesis implicit |
| `"Exarch"`, `"Eater"` | Eldritch implicits |
| `"ScourgeUpside"`, `"ScourgeDownside"` | Scourge mods |
| `"Corrupted"` | Vaal orb corrupted implicits |
| `"DelveImplicit"` | Delve fossil implicits |

Influence mods become eligible when the item has the corresponding influence flag
set AND the base's `influenceTags` table contains a matching key. For example, a
Shaper Jade Amulet gets the virtual tag `"amulet_shaper"` injected into its tag
lookup, allowing Shaper mods that have `weightKey = { "amulet_shaper", … }` to match.

### 3.5 Special Mod Categories

**Essence mods** — always have `weightKey = { "default" }`, `weightVal = { 0 }`.
Weight is always 0 through normal rolling; they are applied only by Essence crafting.

**Crafting bench mods** — stored in `src/Data/ModMaster.lua`. Same tag/weight
structure but normally restricted from natural rolling.

**Veiled mods** — stored in `src/Data/ModVeiled.lua`. Applied by unveiling items
from Betrayal encounters.

**Catalyst quality** — catalysts scale mod values based on `modTags` overlap with
`catalystTags` defined in `src/Classes/Item.lua`. Only mods whose `modTags` contain
a tag matching the catalyst's category are boosted; others are unaffected.

## 4. Item Parsing — From Text to Internal State

When an item is pasted into PoB or loaded from a build file, `Item:ParseRaw()` in
`src/Classes/Item.lua` processes it.

### 4.1 Input Format

Items are represented as plain text in the same format produced by the in-game
Ctrl+C tooltip, with optional PoB-specific metadata fields:

```
Rarity: RARE
Titan's Circle
Jade Amulet
--------
Item Level: 86
--------
+(20-30) to Dexterity        (implicit)
--------
+(43-50) to Strength         (explicit mod line)
+(51-55) to Intelligence
--------
Shaper Item
```

PoB-specific fields not in the game tooltip include:
`Unique ID:`, `Variant:`, `Crafted:`, `Prefix:`, `Suffix:`, `Implicits:`,
`LevelReq:`, `Unreleased:`, `Catalyst:`, `CatalystQuality:`,
`Cluster Jewel Skill:`, `Cluster Jewel Node Count:`, `Talisman Tier:`,
`ArmourBasePercentile:`, etc.

Inline mod flags use brace prefix syntax: `{crafted}`, `{range:0.5}`, `{implicit}`,
`{enchant}`, `{scourge}`, `{crucible}`, `{fractured}`, `{exarch}`, `{eater}`,
`{synthesis}`, `{mutated}`.

### 4.2 Parse Stages

1. **Rarity and name** — first 1–2 lines determine `rarity`, `name`, and `baseName`.
   The parser looks up `data.itemBases[baseName]` to establish `self.base`.
2. **Metadata fields** — `Item Level:`, `Quality:`, `Sockets:`, influence lines
   (`Shaper Item`, etc.), `Crafted: true`, `Prefix: <modId>`, `Suffix: <modId>`, etc.
3. **Mod lines** — remaining lines are passed to `modLib.parseMod()`. Successfully
   parsed lines go into one of several buckets:
   - `self.enchantModLines`
   - `self.implicitModLines`
   - `self.scourgeModLines`
   - `self.explicitModLines`
   - `self.crucibleModLines`
   The parser uses section separators (`--------`) and inline flags to distinguish
   implicit from explicit mods. Unrecognised lines are stored with an empty `modList`
   and flagged as `extra` — PoB will display them but not calculate them.
4. **Quality normalisation** — armour, weapon, and flask items are set to 20%
   quality unless corrupted/mirrored/split.
5. **Crafted item setup** — if `Crafted: true`, the `prefixes` and `suffixes`
   arrays (populated from `Prefix:` / `Suffix:` lines) are resolved against
   `self.affixes` (the eligible mod pool for this base). Unknown modIds are silently
   replaced with `"None"`. Affix count limits are enforced: 2 total for magic, 6
   for rare (4 for jewels/grafts).
6. **`BuildModList()`** — iterates all mod line buckets, applies roll range scaling,
   catalyst quality scalars, and assembles the final internal modifier list used by
   the calculation engine.

### 4.3 Mod Line Resolution

Each recognised text mod line is matched against `modLib.parseMod()`, which walks a
large pattern-matching table built from all known game mod texts. The result is a
`modList` of internal modifier objects (stat name + value) that the calculation
engine consumes directly.

Roll ranges in text (`+(43-50) to Strength`) are resolved using the `range` field
(a 0.0–1.0 interpolation factor). The default `range` is `main.defaultItemAffixQuality`
(configurable in options, default 0.5 = midroll).

## 5. Validation — What PoB Does and Does Not Check

### 5.1 On Import / Paste

**PoB does not validate mod eligibility when parsing item text.** Any mod text that
`modLib.parseMod()` can recognise will be accepted and calculated, regardless of
whether that mod can legitimately spawn on the given base type. You can paste a
sword mod onto a belt and PoB will calculate it.

This is intentional — PoB is a theory-crafting tool, not a game server.

### 5.2 In the Crafting UI

When you use PoB's built-in item crafter (`Crafted: true`), the mod picker is
populated by iterating the full mod pool and calling `GetModSpawnWeight()` for
each candidate. Only mods with `weight > 0` (after the tag matching algorithm in
§3.1) **and** `mod.level <= item.itemLevel` are shown. This is the only place where
true eligibility checking occurs.

### 5.3 Crafted Mod Persistence

When loading a build with a crafted item, if a saved `modId` no longer exists in
the eligible `affixes` pool (e.g. due to a PoB data update), it is silently reset
to `"None"`. No error is raised.

### 5.4 Summary Table

| Scenario | Eligibility enforced? |
|---|---|
| Paste/import item text | No |
| Import character from PoE account | No |
| PoB in-app item crafter (mod picker) | Yes — tag weight + ilvl |
| Loading a saved build | Partial — unknown modIds → None |
| Unique item database | No — stored as raw text, not validated |

## 6. End-to-End Pipeline Summary

```
Content.ggpk
    │
    ▼  bun_extract_file.exe
Data/*.datc64 + Metadata/**/*.txt + Metadata/**/*.it
    │
    ▼  src/Export/Scripts/*.lua  (run once per game patch, inside PoB's engine)
src/Data/Bases/*.lua          ← base type definitions + tags + implicits
src/Data/Mod*.lua             ← mod pool: tiers, weightKey/Val, groups
src/Data/Enchantment*.lua     ← slot-specific enchants, skill-keyed
src/Data/Skills/*.lua         ← active/support skill definitions
src/Data/Gems.lua             ← per-level gem stats
src/Data/Uniques/*.lua        ← raw unique item text blocks
src/Data/StatDescriptions/    ← stat description templates
    │
    ▼  Runtime load (data.itemBases, data.itemMods, …)
PoB calculation engine
    │
    ├─ Item text pasted / loaded
    │       ▼  Item:ParseRaw()
    │   mod lines bucketed → modLib.parseMod() → modList objects
    │   crafted prefix/suffix → resolved against affixes pool (tag-filtered)
    │   → self.modList assembled
    │
    ├─ Crafting UI
    │       ▼  GetModSpawnWeight() for each mod in pool
    │   eligible = weight > 0 AND ilvl >= mod.level
    │   shown in picker; selected modId stored on item
    │
    └─ Calculation engine
            ▼  BuildModList() → CalcPerform()
        stat modifiers summed, scaled by quality/range/catalyst
        → DPS, EHP, resistance totals, etc.
```

## 7. Key Field Reference

### Base type fields

| Field | Type | Meaning |
|---|---|---|
| `type` | string | Item class ("Amulet", "Belt", "Sword", etc.) |
| `tags` | `{ tag = true }` | Spawn tag set used for mod pool lookup |
| `influenceTags` | `{ influence = tag }` | Maps influence name to its virtual tag key |
| `implicit` | string | Implicit mod text with inline roll range |
| `implicitModTypes` | array | Semantic mod-type tags per implicit line |
| `req` | `{ level, str, dex, int }` | Attribute/level requirements |
| `weapon` | table | Base weapon stats |
| `armour` | table | Base armour/evasion/ES stats |

### Mod pool entry fields

| Field | Type | Meaning |
|---|---|---|
| `type` | string | "Prefix", "Suffix", "Corrupted", "1Shaper", "Exarch", etc. |
| `affix` | string | Tier display name |
| `[1]`, `[2]`, … | string | Stat line text with `(min-max)` roll ranges |
| `statOrder` | array of int | Stat ordering indices (for display sorting) |
| `level` | int | Minimum item level for this tier |
| `group` | string | Mutual-exclusion family; one tier per group per item |
| `weightKey` | array of string | Ordered list of tags to match against item |
| `weightVal` | array of int | Parallel spawn weights; 0 = ineligible |
| `weightMultiplierKey` | array of string | Secondary multiplier tag keys (optional) |
| `weightMultiplierVal` | array of int | Multipliers applied as `weight × val / 100` |
| `tags` | array of string | Tags added to the item when this mod is present |
| `modTags` | array of string | Semantic tags (used for catalyst quality scaling) |
